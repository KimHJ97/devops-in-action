# 인프라스트럭처

## 1. Compute Engine

Compute Engine은 맞춤형 컴퓨팅 서비스로, 일반 사용자가 구글 인프라상에서 가상 머신을 구동할 수 있으며, 필요에 따라 알맞은 VM을 생성할 수 있다.

 - `머신 유형`
    - 일반 목적: 비용이 저렴하며 일상적인 컴퓨팅에 적합하다. 가장 적합한 사용 사례는 웹 서비스, 애플리케이션 제공, 백오피스 애플리케이션, 데이터베이스, 캐싱, 미디어 스트리밍, 마이크로서비스, 가상 데스크톱, 개발 환경
    - 컴퓨팅 최적화: 고성능 컴퓨팅, 전자 설계 자동화, 게임, 비디오, 트랜스코딩 및 싱글 스레드 애플리케이션과 같이 최고 성능을 요구하는 작업에 권장
    - 메모리 최적화: SAP HANA와 같은 대규모 내장 메모리 데이터베이스와 같이 매우 큰 메모리 작업, 내장 메모리 분석
    - 가속기 최적화: 머신러닝, 대규모 병렬 계산, 고성능 컴퓨팅과 같은 고성능을 요구하는 작업에 최적화
 - `작동 방식`
    - 종류: 부팅 디스크 이미지, 부팅 디스크 스냅샷, 컨테이너 이미지
    - 이미지는 공용 운영체제 이미지 또는 사용자 정의 이미지를 말한다.
    - 사용자 위치에 따라 가상 머신이 생성되는 영역(Zone)을 정의할 수 있다.
 - `가용성`
    - 고가용성을 위해 Compute Engine은 장애 이벤트 발생 시 다른 리전 또는 영역으로 자동 복구한다.
    - 관리형 인스턴스 그룹은 사전에 정의된 이미지로 인스턴스를 자동으로 복제하여 인스턴스의 지속적인 실행을 보장한다.
    - Compute Engine은 부하 증가 또는 감소에 따라 MIG에서 VM 인스턴스를 자동으로 추가하거나 제거하는 오토스케일링을 제공한다.
 - `보안`
    - 자원들이 서로 연관돼 있지 않아 상호 간의 네트워크 통신이 필요 없다면 서로 다른 VPC 네트워크에서 호스팅하는 것이 좋다.

## 2. Kubernetees Engine

 - `컨테이너를 사용하는 이유`
    - 컨테이너를 사용하면 애플리케이션, 라이브러리, 다른 의존성과 함꼐 패키지화함으로써 서비스형 소프트웨어를 실행할 수 있는 독립적인 환경을 제공한다.
    - VM 접근법으로 하드웨어 스택을 가상화하는 대신, 컨테이너는 운영 시스템 수준에서 가상화하므로 다중의 컨테이너가 OS 커널에서 직접 실행된다.
    - OS 커널을 공유하고 전체 OS를 부팅하는 것에 비해 부팅 시간이 빠르고 메모리 일부만 사용한다.
 - `쿠버네티스 작동 방식`
    - 기본 노드는 클러스터를 제어한다.
    - 워커 노드는 파드(POD)를 실행시킨다.
    - 파드는 컨테이너 집합을 보유한다.
    - 파드는 구성 정보와 하드웨어가 허용하는 한 효율적으로 바이너리를 실행한다.
    - 컨트롤러는 파드가 사양에 따라 실행되도록 보호 기능을 제공한다.
    - 모든 컴포넌트는 고가용성 모드에 배포될 수 있고 데이터 센터나 영역에 골고루 분산될 수 있다.
 - `쿠버네티스 지원 기능`
    - 자동화된 배포와 컨테이너의 복제
    - 컨테이너 클러스터의 온라인 규모 축소와 규모 확장
    - 컨테이너 그룹으로 부하 분산
    - 애플리케이션 컨테이너의 롤링 업그레이드
    - 실패한 컨테이너의 자동화된 재스케줄링을 통한 복원력
    - 클러스터 외부 시스템에 네트워크 포트 노출 제어
 - `쿠버네티스 구축시 어려운 점`
    - 클라우드 공급자 또는 베어메탈 선택
    - 머신 준비
    - 운영체제와 컨테이너 런타임 선택
    - 네트워크 구성
    - 보안 구성
    - DNS, 로깅, 모니터링과 같은 클러스터 서비스 시작
 - `GKE`
    - GKE는 안전한 완전 관리형 쿠버네티스 서비스로, 구글 인프라를 이용해 컨테이너화된 애플리케이션을 배포, 관리하고 확장하기 쉬운 환경을 제공한다.
    - 손댈 필요 없이 무인 오토파일럿 모드로 프로덕션 레디
    - 자사 및 타사 도구를 일관적으로 지원하는 동급 최고의 개발자 도구
    - 고유한 BeyondProd 보안 접근 방식으로 컨테이너 고유 네트워킹 제공
    - 쿠버네티스 API 구현, 네 가지 방식의 오토스케일링, 배포 채널과 멀티 클러스터 지원

## 3. Cloud Run

Cloud Run은 완전 관리형(fully managed) 서버리스 플랫폼으로, 컨테이너 이미지를 실행 가능한 웹 서비스나 API로 손쉽게 배포할 수 있게 해주는 서비스이다.


### Cloud Run 작동 방식

Cloud Run 서비스는 아래와 같은 방식으로 호출할 수 있다.

 - HTTPS
    - Cloud RUn 호스트 서비스를 시작하도록 HTTPS 요청을 전송할 수 있다.
    - 사용자 정의 RESTful 웹 API
    - 비공개 마이크로서비스
    - 웹 애플리케이션의 HTTP 미들웨어 또는 리버스 프록시
    - 사전 패키징된 웹 애플리케이션
 - gRPC
    - gRPC를 사용해 Cloud Run 서비스를 다른 서비스와 연결할 수 있다.
    - 내부 마이크로 서비스 간 통신의 경우
    - 빠른 데이터 적재 지원의 경우
    - 간단한 서비스 정의만 필요하고 전체 클라이언트 라이브러리 작성은 원치 않는 경우
    - gRPC 서버에서 스트리밍 gRPC를 사용해 응답성이 뛰어난 애플리케이션 및 API를 구축하는 경우
 - 웹 소켓
    - 웹 소켓 애플리케이션은 추가적인 구성 없이 Cloud Run에서 지원한다.
    - 사용 사례는 채팅 애플리케이션 같은 스트리밍 서비스가 필요한 모든 애플리케이션이다.
 - Pub/Sub
    - Pub/Sub을 사용해 Cloud Run 서비스의 엔드포인트로 메시지를 푸시할 수 있다.
    - 그러면 메시지는 이후에 HTTP 요청을 통해 컨테이너로 전달된다.
    - Cloud Storage 버킷에 파일을 업로드 후 이벤트를 받고 데이터 변환
    - Cloud Run으로 구글 클라우드 작업 제품군의 로그를 Pub/Sub으로 내보내기
    - Cloud Run 서비스로 사용자 정의 이벤트 배포하고 처리하기
 - 스케줄에 따른 서비스 실행
    - 일정에 따라 Cloud Run을 안전하게 호출하는 Cloud Scheduler를 사용할 수 있다.
    - 정기적인 백업 수행
    - 사이트맵 재생성, 과거 데이터, 콘텐츠, 구성 정보, 동기화, 버전 정보 삭제 등과 같은 반복적인 관리 작업 수행
    - 청구서 또는 다른 문서 생성
 - 동기화 작업 수행
    - Cloud Run 서비스로 비동기적으로 처리할 작업을 안전하게 대기열에 넣는 Cloud Tasks를 사용할 수 있다.
    - 예상치 못한 운영 시스템 사고에 따른 요청 처리
    - 사용자 비접촉성 이벤트를 지연시켜 트래픽 급증 완화
    - 데이터베이스 업데이트 또는 일괄 작업과 같이 느린 백그라운드 작업을 다른 서비스에 위임해 사용자 응답 시간 단축
    - 데이터베이스 및 외부 API와 같은 백엔드 서비스의 호출 비율 제한
 - Eventarc의 이벤트
    - 60개 이상의 구글 클라우드 원본의 이벤트로 Cloud Run을 시작시킬 수 있다.
    - Cloud Storage 이벤트를 사용해 데이터 처리 파이프라인 시작
    - BigQuery 이벤트를 사용해 작업이 완료될 때마다 Cloud Run의 다운스트림 처리를 시작

### Cloud Run과 Cloud Functions 차이점

| 구분            | __Cloud Run__                    | __Cloud Functions__                                |
| ------------- | -------------------------------- | -------------------------------------------------- |
| __기본 개념__     | 컨테이너 기반 서버리스 애플리케이션              | 함수 기반 이벤트 처리 서비스                                   |
| __실행 단위__     | 전체 __컨테이너(Container)__           | 단일 __함수(Function)__                                |
| __언어 제약__     | 없음 — 컨테이너에 들어갈 수 있으면 무엇이든 가능     | Node.js, Python, Go, Java, .NET 등 제한된 런타임만 지원      |
| __트리거 방식__    | HTTP(S) 요청, Pub/Sub, Scheduler 등 | Pub/Sub, Cloud Storage, HTTP, Firebase, Eventarc 등 |
| __상태(State)__ | Stateless (필요시 DB 연동)            | 완전한 Stateless                                      |
| __성능 제어__     | CPU/메모리/동시성(concurrency) 설정 가능   | 동시성 1 (요청당 1개 함수 실행)                               |
| __콜드 스타트 시간__ | 짧음 (몇 백 ms ~ 1초 수준)              | 더 짧거나 유사하지만, 복잡한 함수 많으면 증가                         |
| __복잡도 수준__    | 전체 애플리케이션 구조에 적합                 | 단일 기능 중심의 간단한 로직에 적합                               |
| __배포 단위__     | Docker 컨테이너 이미지                  | 코드 파일 및 종속성(zip 또는 디렉토리)                           |
| __로컬 실행__     | Docker로 완전히 동일한 환경 테스트 가능        | 제한적 (Functions Framework 필요)                       |
| __사용 예시__     | REST API, 웹서버, 백엔드 서비스           | 파일 업로드 이벤트, Pub/Sub 메시지 처리, 알림 트리거 등               |

<br/>

Cloud Run은 서버 전체를 한 개의 컨테이너로 본다. 예를 들어 Spring Boot, Express.js, Flask 등으로 만든 REST API 서버 전체를 그대로 올린다.

Cloud Functions는 하나의 이벤트(하나의 함수 실행). 함수 단위로 코드 작성하고, 각각 독립적으로 동작하며, URL도 각 함수마다 다르다.

## 4. App Engine

App Engine은 애플리케이션 실행에 필요한 인프라를 완전히 자동으로 관리해주는 서비스이다.

| 항목              | 설명                                            |
| --------------- | --------------------------------------------- |
| __관리형 플랫폼__     | 인프라, OS, 런타임, 패치 자동 관리                        |
| __자동 스케일링__     | 트래픽에 따라 인스턴스 자동 증감                            |
| __트래픽 분할__      | 새 버전과 이전 버전 간 트래픽을 나눠 배포 가능                   |
| __버전 관리__       | 여러 버전을 동시에 유지 가능 (롤백 쉬움)                      |
| __HTTPS 기본 지원__ | 자동 TLS 인증서 발급 및 갱신                            |
| __로깅 및 모니터링__   | Stackdriver(=Cloud Logging, Monitoring) 기본 연동 |
| __무료 요금제__      | 일정량 무료 (소규모 프로젝트에 유리)                         |

## 5. Cloud Funtions

Cloud Functions는 GCP의 이벤트 기반(Serverless Functions) 컴퓨팅 서비스로, 함수(Function) 단위로 실행되는 서버리스 환경을 제공한다.

 - 서버를 직접 관리할 필요 없이 이벤트를 트리거(trigger) 로 코드 한 덩어리(Function) 를 실행시킬 수 있습니다.
 - 대표적인 트리거:
    - HTTP 요청
    - Cloud Storage 파일 업로드
    - Pub/Sub 메시지 수신
    - Firestore 문서 변경
    - Cloud Scheduler 호출 등

```bash
┌────────────┐
│ Cloud Storage │
│ (파일 업로드) │
└───────┬────┘
        │ Trigger
        ▼
┌──────────────────┐
│ Cloud Function   │
│  - processImage() │
│  - sendNotification() │
└──────────────────┘
        │
        ▼
┌──────────────────┐
│ Cloud SQL / Pub/Sub │
│ etc. (출력/후속작업) │
└──────────────────┘
```

## 6. VMware Engine

Google Cloud VMware Engine (GCVE)은 기업의 기존 VMware 환경을 그대로 Google Cloud 위에서 실행할 수 있게 해주는 전용 인프라 서비스이다.

 - 온프레미스 VMware 인프라를 GCP로 그대로 옮겨오는 서비스
 - VMware vSphere / vCenter / vSAN / NSX-T 환경을 Google Cloud의 물리 서버(전용 Bare Metal 인프라) 위에서 변경 없이 그대로 실행할 수 있게 해준다.

## 7. 베어메탈 솔루션

Bare Metal Solution (BMS)는 라우드 인프라 위에서 물리 서버(Bare Metal)를 직접 사용하는 전용 서비스로 특정 워크로드(예: Oracle DB, SAP HANA, 고성능 금융 시스템 등) 처럼 가상화가 어렵거나 비효율적인 환경을 위한 솔루션이다.

 - GCP 데이터센터 내에 위치한 전용 물리 서버를 고객 전용으로 제공하는 서비스
 - 가상화(VM) 없이 물리 서버 그대로를 제공
 - GCP의 네트워크·스토리지·보안 인프라와 완전 통합
 - 주로 고성능 DB나 라이선스 제약이 있는 워크로드에 사용
 - GCP 리전 근처 전용 존(Colocation Facility) 에 배치되어 → 지연(latency) 없이 GCP 서비스와 연동 가능
